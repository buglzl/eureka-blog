## 一、你输入网址之后，发生了什么？

**这一章回答：为什么"解析"是一切的第一环。**

你在浏览器输入 `lzleureka.cn`，浏览器并不认识这个名字，它只认 IP 地址（比如 `185.199.108.153`，你可以理解为服务器在互联网上的门牌号）。把"名字"翻译成"门牌号"的过程叫 **DNS 解析**，DNS 就是一本全球通用的电话簿。

查电话簿是分层进行的，像问路：

1. 先问自己：电脑本地有没有记过？（缓存）
2. 再问小区前台：你家宽带运营商的 DNS 服务器（它记过就直接给你）
3. 前台也不知道，就去问管理 `.cn` 的注册局："lzleureka.cn 这个名字归谁家管？"
4. 注册局说："归 Cloudflare 管，你去问 `carter.ns.cloudflare.com`"（这一步的答案叫 **NS 记录**，即"权威名称服务器"，这本电话簿的"官方原版"存放在谁家）
5. Cloudflare 查自己的记录本："门牌号是 185.199.108.153"，回答

关键点有两个：

- **缓存**：每一层的答案都会被记一段时间，下次再问就不用跑全程。记住答案的时长叫 **TTL**（Time To Live，存活时间）。你配的 TTL 10 分钟，意思是全世界的中间人最多帮你记 10 分钟。
- **A 记录**：电话簿里"名字 → 门牌号"这条记录本身。我们配的 8 条 A 记录，就是把 `lzleureka.cn` 和 `www.lzleureka.cn` 都指向 GitHub Pages 的 4 个门牌号。

**所以"域名打不开"的第一排查对象永远是：这本电话簿的某一层出了问题。**

## 二、为什么阿里云解析会拖后腿，Cloudflare 却快？

**这一章回答：GitHub 报 "DNS check unsuccessful" 的根本原因。**

前面说电话簿有"官方原版存放地"（权威名称服务器）。存放地选在哪，决定了全世界的查询多快能得到回答。

- 阿里云默认的存放地（`dns21.hichina.com`）机房在中国境内。国内访问它：毫秒级，飞快。**美国的服务器来问**：数据要跨一个太平洋，我实测一次查询 **2.2 秒**。
- Cloudflare 的存放地遍布全球一百多个城市，但对外只报少数几个名字。你在哪问，就近的节点答应你——这叫**任播（Anycast）**：同一个门牌号，全球多处开门。换成 Cloudflare 后实测 **0.5 秒**。

2.2 秒听起来也能接受？问题在于下一章：GitHub 有个检查员，它的耐心不足 2 秒。

## 三、HTTPS 证书：先证明你是你，再发你证书

**这一章回答：为什么 DNS 慢会导致证书永远签不出来。**

HTTPS 那把小锁的含义是：你和服务器之间的通信被加密，而且**对方真的是你要找的那家**。第二点靠一张**证书**保证——可以理解为服务器的一张身份证，由权威机构（如 Let's Encrypt，一家免费的公益机构）签发。

签发机构发证前必须确认"你真的拥有这个域名"，否则我给 `bank.com` 申请证书假装是银行就乱了。确认方式就是**回头查你的 DNS**：你说这个域名归你？那我查一下电话簿，门牌号指向的确实是你的服务器，就发证。

串起来就是：

```
DNS 检查（限时） → 通过 → 签发证书 → HTTPS 小锁
     ↑
   我卡住的地方：GitHub 的检查员来查电话簿，
   阿里云存放地跨洋应答 2.2 秒 > 检查员的耐心，
   检查员认定"查无此域名"，永远不发证。
```

换 Cloudflare 后 0.5 秒，检查秒过，证书几分钟就签发下来。**这就是同一个域名、什么都没改、只是换了电话簿存放地，HTTPS 就从"卡死"变"秒过"的原因。**

顺带回答一个高频疑问：**为什么我们不用备案？** 备案监管的是"网站服务器放在中国大陆"的情况——你的网站放在 GitHub（境外），不触碰这套体系。备案只在你将来把网站迁回国内服务器时才需要。

## 四、橙云和灰云：Cloudflare 的两种角色

**这一章回答：为什么教程反复强调把记录切成灰色。**

Cloudflare 给每条解析记录配了一个开关：

- **橙云（Proxied，已代理）**：Cloudflare 挡在你的网站前面，访客先到 Cloudflare，Cloudflare 再转给你的真服务器。好处是可加速、可抗攻击；副作用是**访客看到的门牌号变成了 Cloudflare 的**，你的真实服务器被藏起来了。
- **灰云（DNS only，仅 DNS）**：Cloudflare 只当电话簿，查完直接告诉你真实门牌号，流量不经过它。

我们的场景必须用灰云：GitHub 要**根据真实门牌号**做 DNS 检查、发对应的证书。挂着橙云，GitHub 看到的全是 Cloudflare 的地址，签发逻辑就乱了。所以记住一句话：**只想"名字指对"就用灰云，想让 Cloudflare 帮你扛流量才开橙云。**

## 五、搜索引擎是怎么"看到"你的网站的？

**这一章回答：为什么提交 sitemap 会报错，以及为什么报错也不要紧。**

搜索引擎把你的网站送到用户眼前，分三步：

1. **爬取**：爬虫（一种自动化程序）顺着链接在网上爬，发现你的页面
2. **收录**：把爬到的页面存进自己的数据库
3. **排名**：用户搜索时，从数据库里挑出最相关的排前面

帮你爬得更快的有两样东西，都放在你的网站上：

- **robots.txt**：放在网站根目录的"访客须知"，告诉爬虫"哪里可以爬、哪里别爬"，还可以写一行"Sitemap 在哪"
- **sitemap（站点地图）**：一份列出全站所有网址的清单，相当于把整本书的目录递给爬虫，省得它一页页翻

在搜索平台提交 sitemap，本质是**插队**："别等你自己爬了，目录给你，直接来。"它只是加速，不是开关——只要 robots.txt 里声明了 sitemap（我们的博客模板自动生成了），爬虫每次来都会看到。

那为什么我的 sitemap 提交一直报"地址无效"？还是第一章的电话簿问题：你的域名 5 小时前才开始有解析，而电话簿的各层**连"查无此人"的空结果也会缓存**（叫**负缓存**）。Google 手里的还是旧答案"这域名不存在"，自然判为无效。等缓存过期（几小时），重试就通过了。

## 结语

回头看这次踩坑：DNS 慢（第二章）→ GitHub 检查超时 → 证书不发（第三章）→ HTTPS 卡死；新域名负缓存（第一章）→ sitemap 提交报错（第五章）。**没有一个是玄学，全是三件基本事的名字没对上。** 理解了电话簿模型，下次任何域名问题，你都能自己定位到"是哪一层、哪条记录、谁的缓存"。
