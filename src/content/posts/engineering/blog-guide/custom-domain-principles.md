## 〇、全景：绑定域名到底动了哪些环节？

一句话：把 `buglzl.github.io` 变成 `lzleureka.cn`，背后是**三个角色的一次分工调整**。

| 角色 | 一句话职责 | 我们的承担者（迁移前 → 后） |
|---|---|---|
| **注册商** | 域名所有权、实名、续费，登记「解析交给谁」 | 阿里云（不变） |
| **DNS 服务商** | 运营权威服务器，应答全世界的解析查询 | 阿里云云解析（hichina）→ **Cloudflare** |
| **托管平台** | 存放网站文件，响应访问 | GitHub Pages（不变） |

三次变化，只有一次是真正的迁移：

1. **所有权没动**——域名始终在阿里云，实名、续费照旧
2. **解析应答权换了**——登记从 `dns21/22.hichina.com` 改成 `carter/dawn.ns.cloudflare.com`（这两个是应答服务器的**主机名**，不是网址；谁的名字被登记，谁就负责回答全世界的查询）
3. **网站没动**——文件一直在 GitHub

访客视角的一次访问，走的是这条链：**查 DNS 拿到 IP（→ 第一、二章）→ 带 HTTPS 请求 GitHub（→ 证书，第三章）→ 页面返回后被爬虫发现（→ 第五章）**

和操作篇步骤对齐：

| 操作篇步骤 | 动的环节 | 原理章节 |
|---|---|---|
| 第 0 步 摆摊 | GitHub Pages 开张 | — |
| 第 1 步 买域名 + 实名 | 注册商处获得所有权 | 本节 |
| 第 2、3 步 接管解析 | 换权威 DNS | 第一、二章 |
| 第 4 步 绑定 + HTTPS | 托管平台 + 证书 | 第三章 |
| 第 6 步 提交搜索 | 爬虫与收录 | 第五章 |

地图就位。第一站：**DNS——第一环、依赖最多、也是唯一卡住我们的环节。**

## 一、DNS 解析链路

**这一章回答：为什么「解析」是访客链条的第一环，也是坑最深的一环。**

一句话：**DNS（Domain Name System，域名系统）解析，本质上就是把域名翻译成机器能用的地址——对博客来说，就是查出 `lzleureka.cn` 的 IP（Internet Protocol，网际协议）地址。**

浏览器不认识域名，只认 IP。一次解析实际分**两个阶段**：

**阶段一（本机自查）**：查 **① 本机缓存**——浏览器和操作系统各自存着最近查过的「域名 → IP」，命中就直接用，全程不出网。

**阶段二（外包问路）**：没命中，就把问题外包给 **② 递归解析器**。你只发这一次问，剩下的是它的事：**从根服务器问起 → 问 ③ 顶级域 `.cn` → 问 ④ 权威名称服务器**，拿到 IP 交回给你。

每一个答案都会沿途缓存，下次同样的查询在更早的环节就被拦下。下面按 ①②③④ 逐个说清这四个角色。

### ① 本机缓存

浏览器和操作系统各自维护一份「最近查过的域名 → IP」对照表，命中就不再发起网络查询。注意 Chrome 等现代浏览器自带解析器，经常跳过这层直接问 ②。

### ② 递归解析器

一台**替你把后面所有层跑完**的服务器：你只发一次问，它从根服务器起步逐级问路（问根 → 问 ③ → 问 ④），把最终 IP 带回来交给你。它通常由运营商自动分配，也可手动换成公共解析器（`223.5.5.5`、`8.8.8.8`）——后者也是规避运营商解析劫持的常见做法。

一次真实的跑腿过程（你查 `lzleureka.cn` 时，网络上实际发生的对话）：

```text
你的电脑 ──"lzleureka.cn 的 IP 是什么？"──→ 递归解析器

递归解析器查自己的缓存 → 没有或已过期，开始跑腿：
    ├─ 问根服务器:    "lzleureka.cn 谁管？"  → ".cn 归这几台服务器"
    ├─ 问 .cn 服务器: "lzleureka.cn 谁管？"  → "carter/dawn.ns.cloudflare.com"
    ├─ 问 carter:     "lzleureka.cn 的 IP？" → "185.199.108.153 等 4 个"
    └─ 缓存答案（按 TTL，我们的是 10 分钟）

递归解析器 ──"185.199.108.153"──→ 你的电脑
```

### ③ 顶级域 `.cn` 的名称服务器——② 问路的第一站

由 CNNIC（中国互联网络信息中心）运营。它不知道你博客的 IP，只回答一条 **NS（Name Server，名称服务器）记录**：

> 「`lzleureka.cn` 的权威名称服务器是 `carter` 和 `dawn.ns.cloudflare.com`，去问它们。」

这条委托关系，就是你在阿里云「DNS 修改」时改掉的东西。顺带把 NS 记录和 DNS 体系的关系一次说清：**根 → 顶级域 → 你的域名，解析链每一级的衔接都写在 NS 记录里**——它不是 DNS 的附属品，而是 DNS 层级结构的骨架；第二章的耗时差异，比较的正是两段「骨架」所在机房的部署位置。

### ④ 权威名称服务器——问路的终点

唯一真正存放答案的数据库——你在 Cloudflare 面板里配的每一条记录都存在这里。它收到查询，翻出对应的 **A（Address，地址）记录**：`lzleureka.cn` → `185.199.108.153` 等 4 个 GitHub Pages 的 IP，应答给递归解析器，再由它转交给你。**「权威（Authoritative）」的含义：对这个域名的问题，它的回答就是最终解释。**

### 答案回流：一切按 TTL 过期

拿到 IP 后，答案沿原路缓存：递归解析器存一份、你的电脑存一份，第二次访问时 ①② 直接命中，③④ 整层跳过。缓存时长由记录的 **TTL（Time To Live，存活时间）** 决定——我们配的是 10 分钟，而顶级域里 NS 记录的 TTL 是 6 小时，所以换 DNS 服务商后全网彻底生效等的是后者。这些答案在 DNS 里统称为**记录**：每条记录描述一条规则——什么类型、哪个名字、对应什么值。

**推论：任何「域名打不开」问题，先定位是哪一层——① 没命中、② 没命中、③ 委派错了、④ 答案配错了，一一对应。**

## 二、权威 DNS 的部署位置决定海外解析速度

**这一章回答：GitHub 报 `DNS check unsuccessful` 的直接原因。**

先分清两种「解析服务」——我们的链路里两种都出现了：

- **权威解析服务**：存着你在面板写下的记录，被全世界查询。阿里云云解析和 Cloudflare 扮演的就是它
- **递归解析服务**：自己不存你的记录，替你的电脑跑腿去问。运营商 DNS 和 `223.5.5.5` 扮演的是它

本章的耗时对比，说的只是**权威**这种：它的机房部署在哪，决定了全世界查询它的速度：

| 权威 DNS | 海外递归解析器实测耗时 | 结论 |
|---|---|---|
| 阿里云 hichina（`dns21/22.hichina.com`，机房在国内） | **2.2 s** | 超过 GitHub 检查器阈值 |
| Cloudflare（`carter/dawn.ns.cloudflare.com`，全球任播） | **0.5 s** | 通过 |

这里的关键机制是**任播（Anycast）**：Cloudflare 把同一组 IP 宣告到全球三百多个机房，路由协议自动把查询引到最近的节点；而 hichina 的应答来自国内机房，海外查询要跨一个来回。

GitHub 检查域名的超时阈值不足 2 秒（从它返回的 `InvalidDNSError` 和我们的耗时数据反推）。**这不是配置错误，是物理距离问题——换任何一家全球部署的权威 DNS 都能解决，换回国内单点部署的都会复发。**

## 三、HTTPS 证书的签发前提是 DNS 验证

**这一章回答：为什么 DNS 慢会导致证书永远签不出来。**

HTTPS（HyperText Transfer Protocol Secure，安全的超文本传输协议）的信任基础，是一张由 CA（Certificate Authority，证书颁发机构）签发的证书。Let's Encrypt 作为免费的公益性 CA，签发前必须验证申请者对域名的控制权——方式之一就是回查该域名的 DNS 记录，确认解析指向的确实是申请者的服务器。整条链路：

```
DNS 检查（限时） → 签发证书 → 部署到边缘节点 → HTTPS 可用
```

于是第二章的 2 秒超时在这里产生级联后果：检查失败 → 证书申请被拒 → HTTPS 永远不可用。我们实测：迁移 Cloudflare 后检查一次通过，证书几分钟内自动签发。

另一个常见疑问：**为什么这套方案不需要 ICP（Internet Content Provider，互联网内容提供商）备案？** 备案是「网站服务器位于中国大陆」时的行政要求；GitHub Pages 的服务器在境外，不进入这个监管范围。只有将来把站点迁回国内服务器或使用国内 CDN 时，备案才是前置条件。

## 四、橙云与灰云：Cloudflare 的两种角色

Cloudflare 的每条 DNS 记录带一个代理开关：

- **橙云（Proxied）**：流量先进 Cloudflare 边缘网络（CDN〔Content Delivery Network，内容分发网络〕缓存、WAF〔Web Application Firewall，Web 应用防火墙〕、隐藏源站 IP），再回源到真实服务器。访客看到的 A 记录值是 Cloudflare 的 IP
- **灰云（DNS only）**：Cloudflare 只承担权威解析，应答真实 IP，流量不经过它

GitHub Pages 场景必须用灰云：证书签发和域名检查都依赖「A 记录指向 GitHub 的固定 IP（`185.199.108-111.153`）」这一事实。橙云会把记录值替换成 Cloudflare 的 IP，GitHub 的验证对象随之失效。**规则很简单：只需要「名字指对」就用灰云；需要 CDN 的缓存与防护才开橙云。**

## 五、搜索引擎是怎么看到你的网站的？

**这一章回答：为什么提交 sitemap 会报错，以及为什么报错也不要紧。**

搜索引擎把一个页面送到用户眼前分三步：**爬取**（爬虫顺着链接发现页面）→ **收录**（页面进入搜索引擎数据库）→ **排名**（用户搜索时从库中挑选）。前两步有两个站点侧的配合机制：

- **robots.txt**：站点根目录下的抓取策略文件，声明哪些路径允许抓取，并可声明 sitemap 位置
- **sitemap**：全站 URL 清单，让爬虫不必纯靠链接发现页面

先澄清一个常见误会：**robots.txt 不是「防爬虫」的。** 爬虫有两种，态度应当完全相反：

- **搜索引擎爬虫**（Googlebot 等）——免费带客上门的导游，热烈欢迎。挡它 = 主动放弃搜索流量
- **恶意爬虫**（批量抄数据的脚本）——robots.txt 对它们毫无作用（根本不读这个文件），防它靠登录墙、限流、验证码

真实案例：淘宝在 robots.txt 里屏蔽了百度爬虫，于是百度几乎搜不到淘宝商品——不是防不住，是主动放弃百度的导流。我们自己踩的是反向的坑：Fuwari 模板默认写了 `Disallow: /_astro/`，把全站样式和图片挡在 Googlebot 外面——GSC（Google Search Console，谷歌搜索控制台）报告 21 项资源拦下 20 项，页面在 Google 的渲染器里是一堆裸 HTML，封面图无法进入谷歌图片搜索。删除该行即恢复。

在这个背景下看 sitemap 提交报错：「站点地图地址无效」的直接原因是 **DNS 负缓存**。负缓存的机制：DNS 不仅缓存查到的答案，连「查不到」的空应答（**NXDOMAIN**，Non-eXistent DOMAIN，「域名不存在」）也会被各层缓存，时长由权威服务器的 **SOA（Start of Authority，权威起始）记录**决定。你的域名开始解析前，Google 的递归解析器缓存过一次 NXDOMAIN——在它眼里这个域名当时不存在，sitemap 自然「无效」。负缓存过期（小时级）后重试即通过。这也解释了为什么 robots.txt 里声明了 sitemap 就足够：爬虫每次抓取 robots.txt 都会重新发现 sitemap，提交只是插队加速。

## 结语

复盘这次迁移：权威 DNS 部署在国内（第二章）→ GitHub 的 DNS 检查超时 → 证书拒签（第三章）→ HTTPS 当晚卡了几个小时；新域名无解析记录 → 负缓存 → sitemap 提交被拒（第五章）。每一个现象都严格落在「解析快、证书能签、内容可爬」三件事的某一条上，没有一个需要归因于运气。

对同样想折腾自有域名的开发者，这篇的实用结论只有两条：**权威 DNS 选全球任播的厂商；发布新域名后给负缓存留几个小时。**
