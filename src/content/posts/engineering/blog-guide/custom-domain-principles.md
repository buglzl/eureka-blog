## 一、DNS 解析链路

**这一章回答：为什么「解析」是一切的第一环。**

一句话：**DNS（Domain Name System，域名系统）解析，本质上就是把域名翻译成机器能用的地址——对博客来说，就是查出 `lzleureka.cn` 的 IP（Internet Protocol，网际协议）地址。**

浏览器不认识域名，只认 IP。完整的解析要依次经过四层，任何一层命中缓存都可以提前收工：

> **① 本机缓存**（浏览器 + 操作系统）→ **② 递归解析器** → **③ 顶级域 `.cn` 的名称服务器** → **④ 权威名称服务器**

下面逐层拆开。

### 第 ① 层：本机缓存

查询的第一站是你自己的电脑，这里有两份缓存：

- **浏览器缓存**：Chrome/Edge 各自在进程内维护一份 DNS 应答（这也是换了浏览器后「第一次打开变慢」的原因之一）
- **操作系统缓存**：Windows 的 DNS Client 服务（服务名 `Dnscache`）在内存里维护的系统级缓存，本机所有程序共享。查看：`ipconfig /displaydns`；清空：`ipconfig /flushdns`

两个补充事实：其一，`C:\Windows\System32\drivers\etc\hosts` 文件里的手工条目优先级更高，查询前会先比对它；其二，Chrome 等现代浏览器自带解析器，经常跳过操作系统这层直接发起网络查询——所以浏览器访问过的域名，未必出现在 `displaydns` 的输出里。

### 第 ② 层：递归解析器

本机没命中，就会去问「递归解析器」——一台**替你把后面所有层跑完**的服务器：

- 它通常由宽带运营商自动分配（电信/联通各有一批）
- 也可以手动换成公共解析器：阿里 `223.5.5.5`、腾讯 `119.29.29.29`、谷歌 `8.8.8.8`
- 「递归」的含义：你只发一次问，它负责迭代地问完 ③ 和 ④，把最终 IP 带回来交给你

它自己也有缓存，命中同样直接返回。顺带一提，运营商解析器偶发广告劫持，这也是很多人手动换公共解析器的原因。

### 第 ③ 层：顶级域 `.cn` 的名称服务器

递归解析器的缓存也没有，就只能开始正式问路。第一站是 `.cn` 顶级域的名称服务器（由 CNNIC，中国互联网络信息中心运营）。

它不知道你博客的 IP，它只回答一个更小的问题——一条 **NS（Name Server，名称服务器）记录**：

> 「`lzleureka.cn` 这个域名的权威名称服务器是 `carter` 和 `dawn.ns.cloudflare.com`，去问它们。」

**这条委托关系，就是你在阿里云「DNS 修改」时改掉的东西**（从 `dns21/22.hichina.com` 改成 Cloudflare 的两个地址）。

### 第 ④ 层：权威名称服务器

最后一级，也是唯一真正存放答案的数据库——你在 Cloudflare 面板里配的每一条记录，都存在 `carter/dawn` 这两台服务器上。

它收到查询，翻出对应的 **A（Address，地址）记录**：`lzleureka.cn` → `185.199.108.153` 等 4 个 GitHub Pages 的 IP，应答给递归解析器；递归解析器再转交给你。**「权威（Authoritative）」的意思是：对这个域名的问题，它的回答就是最终解释。**

### 答案的回流与缓存

拿到 IP 后，答案沿原路缓存回来：递归解析器存一份（按记录的 TTL）、你的操作系统存一份。第二次访问同一域名，第 ①② 层直接命中，③④ 全部跳过——这就是「第二次打开快很多」的原因。

步骤 ③④ 里查到的答案，在 DNS 里统称为**记录（Record）**——每条记录描述一条规则：什么**类型**、对应**哪个名字**、**值**是什么。后文反复出现的「NS 记录」「A 记录」，指的就是不同类型的规则。

### 两个关键属性：TTL 与负缓存

- **TTL（Time To Live，存活时间）**：每一层的应答都按 TTL（秒数）缓存。我们配的记录 TTL 是 10 分钟，但顶级域里 NS 记录本身的 TTL 是 6 小时——所以更换 NS 服务商后，全网彻底生效要等的是这个 6 小时，而不是记录自己的 10 分钟
- **负缓存**：「查不到」的空应答（**NXDOMAIN**，Non-eXistent DOMAIN，「域名不存在」）同样会被各层缓存，时长由权威服务器的 SOA（Start of Authority，权威起始）记录决定。域名太新、解析还没配好时，各层记住的是「这个域名不存在」——第五章的 sitemap 报错根源在这

**推论：任何「域名打不开」问题，先定位是哪一层出了错——① 没命中、② 没命中、③ 委派错了、④ 答案配错了，一一对应。**

## 二、权威 DNS 的部署位置决定海外解析速度

**这一章回答：GitHub 报 `DNS check unsuccessful` 的直接原因。**

权威名称服务器的机房在哪，决定了全世界离它多远：

| 权威 DNS | 海外递归解析器实测耗时 | 结论 |
|---|---|---|
| 阿里云 hichina（`dns21/22.hichina.com`，机房在国内） | **2.2 s** | 超过 GitHub 检查器阈值 |
| Cloudflare（`carter/dawn.ns.cloudflare.com`，全球任播） | **0.5 s** | 通过 |

这里的关键机制是**任播（Anycast）**：Cloudflare 把同一组 IP 宣告到全球三百多个机房，路由协议自动把查询引到最近的节点；而 hichina 的应答来自国内机房，海外查询要跨一个来回。

GitHub 检查域名的超时阈值不足 2 秒（从它返回的 `InvalidDNSError` 和我们的耗时数据反推）。**这不是配置错误，是物理距离问题——换任何一家全球部署的权威 DNS 都能解决，换回国内单点部署的都会复发。**

## 三、HTTPS 证书的签发前提是 DNS 验证

**这一章回答：为什么 DNS 慢会导致证书永远签不出来。**

HTTPS（HyperText Transfer Protocol Secure，安全的超文本传输协议）的信任基础，是一张由 CA（Certificate Authority，证书颁发机构）签发的证书。Let's Encrypt 作为免费的公益性 CA，签发前必须验证申请者对域名的控制权——方式之一就是回查该域名的 DNS 记录，确认解析指向的确实是申请者的服务器。整条链路：

```
DNS 检查（限时） → 签发证书 → 部署到边缘节点 → HTTPS 可用
```

于是第二章的 2 秒超时在这里产生级联后果：检查失败 → 证书申请被拒 → HTTPS 永远不可用。我们实测：迁移 Cloudflare 后检查一次通过，证书几分钟内自动签发。

另一个常见疑问：**为什么这套方案不需要 ICP（Internet Content Provider，互联网内容提供商）备案？** 备案是「网站服务器位于中国大陆」时的行政要求；GitHub Pages 的服务器在境外，不进入这个监管范围。只有将来把站点迁回国内服务器或使用国内 CDN 时，备案才是前置条件。

## 四、橙云与灰云：Cloudflare 的两种角色

Cloudflare 的每条 DNS 记录带一个代理开关：

- **橙云（Proxied）**：流量先进 Cloudflare 边缘网络（CDN〔Content Delivery Network，内容分发网络〕缓存、WAF〔Web Application Firewall，Web 应用防火墙〕、隐藏源站 IP），再回源到真实服务器。访客看到的 A 记录值是 Cloudflare 的 IP
- **灰云（DNS only）**：Cloudflare 只承担权威解析，应答真实 IP，流量不经过它

GitHub Pages 场景必须用灰云：证书签发和域名检查都依赖「A 记录指向 GitHub 的固定 IP（`185.199.108-111.153`）」这一事实。橙云会把记录值替换成 Cloudflare 的 IP，GitHub 的验证对象随之失效。**规则很简单：只需要「名字指对」就用灰云；需要 CDN 的缓存与防护才开橙云。**

## 五、搜索引擎是怎么看到你的网站的？

**这一章回答：为什么提交 sitemap 会报错，以及为什么报错也不要紧。**

搜索引擎把一个页面送到用户眼前分三步：**爬取**（爬虫顺着链接发现页面）→ **收录**（页面进入搜索引擎数据库）→ **排名**（用户搜索时从库中挑选）。前两步有两个站点侧的配合机制：

- **robots.txt**：站点根目录下的抓取策略文件，声明哪些路径允许抓取，并可声明 sitemap 位置
- **sitemap**：全站 URL 清单，让爬虫不必纯靠链接发现页面

先澄清一个常见误会：**robots.txt 不是「防爬虫」的。** 爬虫有两种，态度应当完全相反：

- **搜索引擎爬虫**（Googlebot 等）——免费带客上门的导游，热烈欢迎。挡它 = 主动放弃搜索流量
- **恶意爬虫**（批量抄数据的脚本）——robots.txt 对它们毫无作用（根本不读这个文件），防它靠登录墙、限流、验证码

真实案例：淘宝在 robots.txt 里屏蔽了百度爬虫，于是百度几乎搜不到淘宝商品——不是防不住，是主动放弃百度的导流。我们自己踩的是反向的坑：Fuwari 模板默认写了 `Disallow: /_astro/`，把全站样式和图片挡在 Googlebot 外面——GSC（Google Search Console，谷歌搜索控制台）报告 21 项资源拦下 20 项，页面在 Google 的渲染器里是一堆裸 HTML，封面图无法进入谷歌图片搜索。删除该行即恢复。

在这个背景下看 sitemap 提交报错：「站点地图地址无效」的直接原因是 Google 的**解析负缓存**——域名开始解析前，Google 的递归解析器缓存了 NXDOMAIN（域名不存在），缓存过期前它连站点都访问不到。负缓存过期（小时级）后重试即通过。这也解释了为什么 robots.txt 里声明了 sitemap 就足够：爬虫每次抓取 robots.txt 都会重新发现 sitemap，提交只是插队加速。

## 结语

复盘这次迁移：权威 DNS 部署在国内（第二章）→ GitHub 的 DNS 检查超时 → 证书拒签（第三章）→ HTTPS 卡死两天；新域名无解析记录 → 负缓存 → sitemap 提交被拒（第五章）。每一个现象都严格落在「解析快、证书能签、内容可爬」三件事的某一条上，没有一个需要归因于运气。

对同样想折腾自有域名的开发者，这篇的实用结论只有两条：**权威 DNS 选全球任播的厂商；发布新域名后给负缓存留几个小时。**
