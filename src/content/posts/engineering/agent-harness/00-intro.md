> 系列笔记，基于论文 [Agent Harness Engineering: A Survey](https://openreview.net/forum?id=3hXEPbG0dh)（TMLR Long）。这不是翻译，是我的阅读记录：每篇会带着我自己的问题去读，对照真实的 agent 系统（Claude Code、MCP、Agent SDK……）来验证论文的说法。

# 从一个现象说起

同一个底层模型，放进不同的 agent 产品里，表现可以天差地别：任务成功率、成本、稳定性完全不在一个量级。模型明明是同一个，差在哪？

这篇论文给出的答案很直接：**任务执行的可靠性，与其说取决于模型本身，不如说取决于包裹着模型的那层基础设施——harness。**

Harness 是什么？粗略地说，就是模型之外的所有东西：工具怎么接、上下文怎么管、循环怎么驱动、出错怎么兜底、行为怎么约束。模型是引擎，harness 是整辆车。引擎再好，没有变速箱和悬挂也上不了路。

:::note
论文信息：*Agent Harness Engineering: A Survey*，TMLR 长文（正文 12+ 页）。定位是对 harness 工程的系统性、基于实践的综述——把 harness 从"实现细节"提升为**一等公民的系统层**来研究。
:::

# 论文的三个主张

整篇论文围绕三个贡献展开，我的系列也按这个骨架来组织：

1. **Harness 是一个独立的系统层。** 它有自己的演进史（三次工程范式迁移）、自己的横切矛盾，和一批尚未解决的开放问题。
2. **ETCLOVG 七层分类法。** 把任何 harness 拆成七个可分析的层：执行环境、工具接口、上下文管理、生命周期/编排、可观测性、验证、治理。
3. **生态映射与生产经验。** 把 170+ 个开源项目映射到这套分类法上，并提炼 OpenAI、Anthropic、LangChain 等在生产环境中的工程原则。

# 三次范式迁移

论文梳理的这条演进线，我理解是全篇的叙事主线：

| 阶段 | 关注对象 | 典型问题 | 代表性实践 |
| --- | --- | --- | --- |
| Prompt Engineering | 单次调用的措辞 | "怎么问，模型才答得好" | few-shot、思维链、角色设定 |
| Context Engineering | 整个上下文窗口 | "窗口有限，该放什么进去" | RAG、压缩、记忆系统 |
| Harness Engineering | 模型之外的整个系统层 | "怎么让 agent 在长任务里持续可靠" | 工具设计、编排循环、沙箱、evals |

每次迁移都不是替代前一个，而是把前一个变成自己的子问题——harness 工程里当然还要写 prompt，但决定成败的已经不只是 prompt 了。

# ETCLOVG：harness 的七层视图

这是论文的核心工具，也是这个系列的骨架。任何 harness 都可以拆成这七层：

| 层 | 缩写 | 回答的问题 |
| --- | --- | --- |
| 执行环境 | E | agent 的代码在哪里跑？隔离和资源怎么管？ |
| 工具接口 | T | 模型能做什么动作？接口怎么设计模型才用得好？ |
| 上下文管理 | C | 什么信息、以什么形式、在什么时机进入上下文？ |
| 生命周期/编排 | L/O | agent loop 怎么驱动？子任务、子 agent 怎么组织？ |
| 可观测性 | O | agent 在干什么、为什么这么干，怎么看？ |
| 验证 | V | 怎么知道 harness 改好了还是改坏了？ |
| 治理 | G | 权限、安全、合规怎么控制？ |

后面每一层（或相邻两层的组合）各成一篇文章展开。

# 贯穿全文的张力

论文反复回到三对矛盾上，先在这里立个 flag，看后面各篇怎么回应：

- **成本-质量-速度三难**：三者很难同时占优，工程上永远在权衡；
- **能力-控制权衡**：给 agent 越多的自主性，越难约束它的行为边界；
- **harness 耦合问题**：harness 和模型耦合太深——换模型、升模型，harness 可能要跟着重写。

# 这个系列怎么写

每篇固定四段结构，为了逼自己不写成论文缩写：

1. **问题**：读这篇时我带着什么疑问（见文末问题清单）；
2. **论文说了什么**：该层的核心概念和机制；
3. **对照真实系统**：拿一个我摸过的 harness 验证论文说法；
4. **遗留问题**：没想通的、论文没答的，留给后面或收官篇。
